# はじめに

ローカルLLMを Mac 上で試したいと思っても、最初に詰まりやすいのはモデルそのものより周辺の整理でした。どこに記録を残すのか、GitHub を何のために使うのか、Codex に何を任せるのかが曖昧なままだと、検証を始めても後で振り返りにくくなります。

今回やったのは、ローカルLLMの本格導入そのものではなく、その前段の土台づくりです。固定費をできるだけ抑えながら Mac 上で検証を進める前提を整理し、Obsidian・GitHub・Codex で回すための最小構成を整えました。

先に結論を書くと、最初に整えるべきなのはモデルの比較表よりも「記録」「履歴」「公開」の導線でした。ここが曖昧だと、あとで試行錯誤が散らばって再利用しにくくなります。

この記事では、次の 3 点を整理した過程をまとめます。

- Obsidian をどの粒度で使い分けるか
- GitHub を何のために使うか
- Codex をどこまで実務支援に寄せるか

# 今回やったこと

## 1. 最初は小さく検証する方針にした

最初から大きな自動化や複雑な連携を入れると、どこで詰まっているのか分かりにくくなります。そこで今回は、低コストで小さく検証することを優先し、Slack 連携のような周辺機能は後回しにしました。

実行環境は `Ollama Desktop` を起点に考えつつ、必要に応じて他の候補と比較する前提にしています。まずは「続けて検証できる状態」を作ることを優先しました。

## 2. 記録の置き場所を分けた

作業ログを全部 Daily ノートだけに押し込むと、あとで再利用しにくくなります。そこで Obsidian では、役割ごとに記録を分ける構成にしました。

- `Daily`: その日の作業ログ
- `Projects`: プロジェクト単位の方針や途中整理
- `Context`: AI に渡す圧縮済みの前提情報

この分け方にすると、その場の試行錯誤と、後から使い回したい判断材料を切り分けやすくなります。

イメージとしては次のような分担です。

```text
Obsidian
├── Daily      その日の作業ログ
├── Projects   テーマごとの意思決定や方針
└── Context    AI に渡すための整理済み前提
```

## 3. GitHub と Codex の役割を整理した

最初は「GitHub と連携すれば作業ログもある程度自動化できるのでは」と思っていましたが、実際にはそうではありませんでした。GitHub は主に保存、履歴管理、同期、公開のための基盤として使うものです。

一方で Codex は、まずローカル作業の支援に寄せるのが自然でした。たとえば次のような用途です。

- 作業フォルダの初期整備
- Markdown ファイルの整形
- README や手順書の作成
- 公開用ディレクトリの整備

今回の整理でも、README、テンプレート、公開用フォルダなどの初期構成づくりに使いました。

# 実際に詰まったこと

## `Ollama` 周辺の前提が思ったより曖昧だった

ローカルLLMを始める段階では、モデル選定そのものよりも「何をどこまでローカルで回したいのか」の前提が曖昧でした。たとえば `Ollama` を起点にする方針は決めても、比較対象をどこまで広げるかはまだ固まっていません。

また、Ollama 上の実行環境と Codex のような支援ツールを、実際の運用の中でどう住み分けるかも最初はかなり分かりづらく感じました。ここは言葉だけで整理するより、実際に試しながら具体化していく必要があります。

## GitHub 連携への期待値がずれていた

GitHub とつなげば作業ログまで自動で整うような印象を持っていましたが、実際にはそうではありませんでした。履歴管理と公開導線は整えられても、何を残すか、どう整形するかという運用は自分で設計する必要があります。

この点を先に理解できたことで、「メモは Obsidian に残し、公開物だけ GitHub に載せる」という役割分担が明確になりました。

# 整理できたこと

今回の整理で一番大きかったのは、道具ごとの役割を切り分けられたことです。

- Obsidian は、作業ログ、判断理由、AI 用コンテキスト、公開下書きを集約する母艦
- GitHub は、差分と履歴を追うための基盤
- Codex は、ローカル構成整備や Markdown 運用を補助する実務支援

この切り分けができると、「どこに何を残すべきか」がかなり分かりやすくなります。特に、最初から全部を自動化しない方針を取れたのは大きかったです。

Daily を 1 日 1 ノートで残し、作業後に AI で整形し、必要なものだけ Project や Context に反映する流れにすると、運用しながら少しずつ改善できます。

要するに、最初に必要なのは「完成形」ではなく「育てられる最小構成」でした。

# 今後の進め方

次は `Ollama Desktop` を起点にして、最初の検証観点をひとつ決めて小さく試す予定です。その結果を Daily に残し、整理した内容だけを Project と Context に反映します。

公開できそうな内容が出てきたら、今回整えた `05_Public/zenn` から `zenn-content/articles` へ移し、Zenn の公開記事として仕上げます。

# まとめ

ローカルLLMの導入は、モデル選定や性能比較だけでなく、記録と再利用の導線をどう作るかで進めやすさが大きく変わると感じました。

まずは検証を始める前の足場を作ることに集中し、Obsidian・GitHub・Codex の役割分担を整理したことで、次の実験に進みやすくなりました。これからローカルLLMを試すなら、いきなり全部つなげるのではなく、最小構成で土台を整えるところから始めるのがよさそうです。

同じように「まず何から整えるべきか」で迷っているなら、モデル選定より先に、記録の置き場所と公開導線を決めておくと後がかなり楽になります。
