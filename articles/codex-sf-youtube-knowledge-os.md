# はじめに

「SF思考実験室」という、SFを入口に科学・哲学・社会を考えるYouTubeチャンネルを作り始めた。

最初に決めたのは、動画を量産することを最終目標にしないことだった。動画はあくまでアウトプットの一つで、残したいのは調べた根拠、そこから導いた主張、反論、そして思考実験の境界である。

その知識が残れば、同じテーマから動画だけでなく、ブログ記事や書籍原稿も作れる。そこで既存の動画編集ツールを、**テーマから知識・台本・本編・ショート・投稿情報までをつなぐ制作OS**へ作り替えることにした。

この記事では、Codexと一緒にローカル環境で組み立てた設計と、実際に運用して見えた課題をまとめる。

# 目標は「動画生成ツール」ではなく知識OS

教養系の動画では、もっとも避けたいのが、もっともらしい想像を科学的事実のように話してしまうことだ。

たとえば「重力が3倍の惑星で人間はどんな形に進化するか」は面白い問いだが、未来の生物の形を観測した事実ではない。一方で、重力と骨・筋肉への負荷、体の大きさと支持構造の関係には、既存の知見がある。

そこで、テーマごとに少なくとも次の層を残す方針にした。

```text
Source      論文・書籍・公的機関などの出典
Evidence    出典から確認できる観測・研究結果
Claim       動画内で伝える、根拠に支えられた主張
Hypothesis  科学的に有力だが未確定の仮説
Speculation SFとして広げる考察・思考実験
```

この区別をデータとして持つと、台本を書くときに「ここまでは研究の話」「ここからは条件を置いた想像」と明示できる。動画の説得力を上げるだけでなく、後から調査を更新しやすい。

# テーマからアウトプットまでの流れ

今回の制作パイプラインは、次のように分けている。

```text
テーマ
  ↓
Source → Evidence → Claim を含む Knowledge Base
  ↓
会話台本 / Scene設計 / 画像・動画の指示
  ↓
音声生成 / 素材割り当て / BGM
  ↓
本編MP4 / Shorts MP4 / サムネイル / 投稿メタ情報
  ↓
YouTube・ブログ・書籍用の再利用
```

ポイントは、一本の動画を手作業の編集データとして閉じないことだ。台本、発話、話者、Scene、音声ファイル、素材の関係をタイムラインとして構造化する。

すると「字幕を直す」ではなく、「この発話の根拠ラベルを直す」「このSceneの視覚素材を差し替える」「ショートのフックを直す」と、変更の対象を限定できる。

# 最初の題材：太陽系外惑星に知的生命体がいたら、どんな社会になるのか？

最初の長尺テーマには、次の問いを選んだ。

> 太陽系外惑星に知的生命体がいたら、どんな社会になるのか？

この問いにいきなり「異星人の性格」や「政治制度」で答えない。環境から順番に積み上げる。

1. 恒星と惑星の条件
2. 昼夜や気候の安定性
3. 生態系と利用できるエネルギー
4. 身体、感覚、情報伝達
5. 協力・分業・都市
6. 価値観と哲学

たとえば、潮汐固定で昼と夜が固定される可能性を扱うときも、「住める場所は恒星からの距離だけで決まらない」と言い切るのでは足りない。誰にとって住めるのか、熱の運ばれ方や大気はどう影響するのか、生命の存在は確認されているのかを順に説明する必要がある。

この順序を決めておくと、SF的な飛躍を楽しみながらも、どの条件から社会の違いを導いたのかを見失いにくい。

# 既存の動画編集ツールをどう作り替えたか

もともとは、ゲーム制作ログ向けの半自動編集ツールがあった。台本、画面録画、立ち絵、BGMをまとめ、Remotionで本編とショートを出力する仕組みである。

SF教養チャンネルでは、ゲーム録画の代わりに、Sceneごとの解説画像や図解が中心になる。そのため、次の役割を追加・変更した。

```text
knowledge-base/topics/
  テーマ、出典、根拠、主張、反論、台本、Scene設計

public/video/generated/
  生成済みの音声、タイムライン、プロジェクト設定

video-input/
  BGM、サムネイル、Scene用の画像・動画素材

scripts/knowledge/
  根拠・台本・構成を検査する処理

scripts/video/
  音声生成、タイムライン生成、GUIサーバー、書き出し処理
```

動画の見た目を先に作り込むより、テーマとデータ構造を先に固めた。これにより、音声合成を入れ替える、素材の生成方法を変える、ブログへ出力する、といった変更を動画全体の作り直しにせずに済む。

# 本編とショートは「同じものを縮めない」

本編とショートは同じ知識を使うが、同じ動画ではない。

本編では、前提を置き、反論や不確実性も示しながら結論へ進む。ショートでは、問いを一つに絞り、最初の数秒で「なぜ気になるのか」を出す。

```text
本編
  問い → 前提 → 根拠 → 条件ごとの考察 → 境界の明示 → 結論

ショート
  強い問い → 意外な前提 → 一つの考察 → 本編への導線
```

同じテーマID、同じ出典、同じ用語定義を共有しながら、台本とSceneの設計は分ける。これが「長尺をそのまま切り抜いたショート」にならないための基本ルールになった。

# サムネイルとエンディングを別管理しない

最初の実装では、エンディングに以前の動画の画像やロゴが残る問題が起きた。原因は、サムネイルとエンディング背景を別々の設定として扱っていたことだった。

そこで、教養動画では次の不変条件を設けた。

```text
YouTube用サムネイルを生成する
  ↓
同じ画像をエンディング背景に使う
  ↓
エンディングに旧チャンネルのロゴ・QR・CTAを混ぜない
```

「最後に何を表示するか」もコンテンツの一部である。見た目のルールを仕様にし、書き出し前に検査することで、古い素材が混ざる事故を減らせる。

# 自動化で一番重要だったのは品質ゲート

最初は、テーマを入力したら一回で動画が出ることを目指していた。しかし実際には、単に書き出せることと、視聴できる品質であることは別だった。

特に問題になったのは次の点である。

- ボケとツッコミの順番が逆で、会話の意味が通らない
- 視聴者役のキャラクターが、急に専門家のように説明する
- セリフと関係のない背景画像が出る
- セクションの間が長すぎて、動画が止まったように見える
- 音声の末尾が次のセリフへの切り替えで途切れる
- 以前のチャンネル素材がエンディングに残る

これらは、人がプレビューすればすぐ分かる。しかし、生成処理だけでは見落としやすい。そこで「生成」と「出力」の間に品質ゲートを置いた。

## 現在入れているチェック

### 台本

- 1セリフを長くしすぎない
- 専門用語は初出で短く言い換える
- 抽象語だけで結論を済ませない
- 視聴者役は質問・驚き・素朴なツッコミを担当する
- 事実、仮説、SF的考察の境界を残す

### タイムライン

- 各セクションの冒頭に約1秒の入りを置く
- セクション間の無音が長くなりすぎないよう検査する
- 音声ファイルの実際の長さで発話区間を作る
- 再生時計が先行しても、前の音声を途中で切らない

### 素材とエンディング

- Sceneごとに、セリフの主題と対応する画像・図解を設定する
- 教養動画のエンディングは当該動画のサムネイルを使う
- 旧ロゴやQRコードを含むテンプレートを混ぜない

すべてを自動判定できるわけではない。それでも「壊れているものを出力しない」ルールをコードで持つだけで、修正の往復はかなり減る。

# ローカルGUIは、完成前の確認場所

GUIでは、台本、各Sceneの素材、音声、BGM、タイムラインを一画面で確認できるようにしている。

重要なのは、GUIが単なる設定画面ではないことだ。書き出した動画を見てから直すのでは遅い。出力前に、次の問いへ答えられる状態にする。

- このセリフに、この画像は本当に合っているか
- 次の章へ入る間は長すぎないか
- 音声と字幕は同じ内容を同じタイミングで伝えているか
- この結論は、根拠からどこまで言えるのか

ネイティブアプリとしても起動できるようにし、ブラウザのタブを探さず制作画面を開けるようにした。起動判定や音声再生のような地味な部分も、制作フローでは重要だった。

# 「一発で作る」は、確認をなくすことではない

テーマを渡すと本編・ショート・サムネイル・投稿情報まで作れる状態は目指している。ただし、それは人間の確認をなくすという意味ではない。

人が見るべきなのは、主に次の三つだ。

1. 根拠と結論の距離が適切か
2. 会話として面白く、初見でも理解できるか
3. 画像・図・演出がセリフの理解を助けているか

自動化すべきなのは、毎回同じ手順を再現する部分と、明確に失敗と分かる部分の検査である。判断を自動化しすぎるのではなく、人が判断すべき場所を見つけやすくする。

# 次にやること

次の段階では、公開後のYouTube AnalyticsをKnowledge Baseと結びつけたい。

たとえば、宇宙文明のテーマはクリックされやすいのか、生物進化のテーマは視聴維持率が高いのか、哲学テーマはコメントされやすいのかを、動画の内容と一緒に見られるようにする。

最終的には、再生数だけを追うのではなく、知識の深さと視聴者の反応を両方見ながら、「次に考える価値のある問い」を提案できる制作OSに育てたい。

# まとめ

今回作っているのは、動画を自動で面白くする魔法のボタンではない。

テーマ、根拠、台本、素材、音声、動画、投稿後の反応を切り離さず、しかし混ぜすぎずに扱うための土台である。

SFは自由な想像を楽しめるジャンルだ。その自由を雑な断定にしないために、どこからが分かっていることか、どこからが思考実験かを残しておく。その積み重ねが、YouTube一本だけで終わらない知識資産になると考えている。
