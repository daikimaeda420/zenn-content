# はじめに

RPG Maker MZで、政治サスペンス型の育成バトルRPGを作り始めました。

タイトルは仮ではなく、今の方針として次に決めています。

```text
BABEL-LINK 2060: 調律者の記録
```

この記事では、Codexを使って、世界観資料、データベース設計、イベント導線、テスト修正まで進めた記録をまとめます。

まだビジュアルやUIは仮です。今やっているのは、ゲームとして成立する最小導線を先に組む段階です。

# ゲームの方向性

本作は、2060年のAI管理社会を舞台にしたRPGです。

中央政権AI「バビロン」が、市民等級、移動、労働、情報、フィジカルAIの運用を管理しています。主人公は下層市民出身の調律師で、フィジカルAIを契約、育成しながら市民等級ライセンスを上げ、中央区を目指します。

バトルの土台は、ポケモン的な「相性」「育成」「契約AIの編成」を意識しています。ただし、捕獲ではなく「契約」「同期」「調律」という世界観に置き換えています。

初期の体験版で出すフィジカルAIは次のようにしました。

| 名前 | 属性 | 役割 |
| --- | --- | --- |
| エコー | 情報/生体 | 初期パートナー、解析、回復 |
| リベット | 産業 | 耐久、物理攻撃、ギミック解除 |
| シグナル | 情報 | 弱体、命中補助、ログ解析 |
| ラスト | 反逆 | 体験版では伏線 |

# まず資料を作った

最初にやったのは、MZで直接マップを作り込むことではありません。

次の資料を作って、ゲームの基準を固めました。

```text
docs/SETTING_BIBLE.md
docs/VISUAL_BIBLE.md
docs/DEMO_SPEC.md
docs/AI_COMPANION_SPEC.md
docs/PHYSICAL_AI_DATA.md
docs/MZ_BATTLE_DATABASE_PLAN.md
docs/MZ_BATTLE_BALANCE_PLAN.md
docs/MZ_DATA_MAP.md
```

特に重要なのは `SETTING_BIBLE.md` です。旧ファンタジー案は参考資料として残しつつ、今後の正設定はBABEL-LINK 2060側に寄せました。

RPG Maker MZは、エディタ上で直接作ると速い一方で、あとから「どのスイッチが何だったか」「どのイベントがどこにあるか」が分かりにくくなりがちです。

そのため、先にMarkdownでID設計を作りました。

# 属性相性を決めた

体験版の属性は、まず5つに絞りました。

```text
情報 → 産業 → 生体 → 秩序 → 反逆 → 情報
```

矢印の先に強い、というループです。

倍率はシンプルにしました。

| 種別 | 倍率 |
| --- | --- |
| 弱点 | 1.5倍 |
| 通常 | 1.0倍 |
| 耐性 | 0.75倍 |

複雑すぎる相性表にすると、体験版の段階ではプレイヤーも制作者も扱いきれません。最初は、少数の属性で「スキャンすると有利不利が見える」体験を作る方針にしました。

# パルススキャンと倍率表示

エコーの技として、`パルススキャン` を作りました。

これは弱点を有効化する技ではなく、敵の属性、弱点、耐性を見えるようにする技です。

スキャン後は、技選択画面で次のように倍率を表示します。

```text
ノイズパルス x1.50
リベットパンチ x0.75
ログピアス x1.50
```

実装では、MZのメモタグを使っています。

```text
<pulseScan>
<aiElement: 情報>
<aiWeak: 情報>
<aiResist: 反逆, 産業>
```

この処理は `js/plugins/ProjectRPG_Core.js` に寄せ、スキルや敵のデータベースとは分離しました。

# データベースをスクリプトで反映した

RPG Maker MZのデータベースはエディタから手で編集できます。

ただ、今回はアクター、クラス、スキル、ステート、敵、トループ、属性名、スイッチ、変数まで一気に変える必要がありました。

手作業だとミスが出やすいため、反映スクリプトを作りました。

```bash
node tools/apply-battle-database.mjs
```

これで、たとえば次のようなIDをまとめて設定します。

| 種別 | ID例 |
| --- | --- |
| スキル | 301 パルススキャン |
| スキル | 343 ログピアス |
| ステート | 31 解析済み |
| 敵 | 5 フォージA17 |
| トループ | 5 BLK_EV027_ユリア認可戦 |

MZはJSONファイルを持っているので、設計さえ決めれば一括反映しやすいです。

# 体験版導線もスクリプトで作った

次に、体験版の最小プレイアブル導線を作りました。

イベントは仕様書上で `EV001` から管理しています。

| マップID | マップ名 | 実装範囲 |
| --- | --- | --- |
| Map190 | 主人公の作業部屋 | EV001〜EV003 |
| Map191 | 下層居住区 | EV004〜EV005、EV011〜EV012 |
| Map192 | 廃棄場 | EV006〜EV010 |
| Map193 | 労働区入口 | EV013 |
| Map194 | 労働区工場 | EV014〜EV018、EV022〜EV023 |
| Map195 | 廃棄ライン | EV019〜EV021 |
| Map196 | 認可戦会場 | EV024 |

反映コマンドは次です。

```bash
node tools/apply-demo-prologue-events.mjs
```

サンプルマップを直接壊さないように、新規のMap190〜196へ体験版導線を作る方針にしました。

# 監査スクリプトも作った

外部スクリプトでMZのJSONを編集すると、壊れていてもエディタを開くまで気づきにくいです。

そこで、最低限のチェック用スクリプトを用意しました。

```bash
node tools/audit-project.mjs
```

このスクリプトでは、次のような項目を確認します。

- 主要JSONがパースできるか
- `ProjectRPG_Core` が登録されているか
- `パルススキャン` や `フォージA17` が想定IDにあるか
- 開始位置が Map190 `(11,11)` か
- EV001〜EV024のイベント名が存在するか

手作業の見落としを減らすために、こういう監査スクリプトはかなり重要でした。

# プレイテストで直したこと

実装後は、実際にプレイして詰まった場所を直していきました。

たとえば、次のような問題が出ました。

- 廃棄場にエコーがいない
- 労働区入口から戻れない
- 労働区入口が探索できない
- 工場の一部で動けなくなる
- シグナルにたどり着けない
- 端末防衛AIが強すぎる
- 認可戦前に回復できず、ボスまでに消耗する

この段階では、見た目の完成度よりも「導線が詰まらないこと」を優先しました。

ユーザーが実際に画面を見ながら「ここから動けない」「敵が倒せない」と報告し、Codex側でイベント位置、通行設定、敵ステータス、回復導線を調整する流れです。

# まだ仮の部分

現時点で、バトル画面やUIはまだMZ標準に近いです。

将来的には、もっとポケモン的な見せ方に寄せたいです。

- 戦闘UIをフィジカルAIバトルらしくする
- 技選択画面を見やすくする
- 解析済みの敵に倍率を分かりやすく表示する
- AR UIやチップ回線の雰囲気を入れる
- フィジカルAIの立ち絵やドットを差し替える

ただし、最初から見た目を作り込むと、導線や仕様が変わった時に作り直しが増えます。

そのため、まずは仮素材で「ゲームとして進むか」を優先しています。

# RPG Maker MZとCodexの相性

今回やってみて、MZとCodexの相性はかなり良いと感じました。

理由は、MZのプロジェクトがJSON中心で、仕様書とスクリプトを往復しやすいからです。

特に向いていた作業は次です。

- スイッチと変数のID設計
- スキル、敵、トループの一括反映
- イベント名の命名規則化
- マップIDとイベントIDの対応表作成
- 監査スクリプトの作成
- プレイテストで見つかった詰まりポイントの修正

一方で、マップの見た目、キャラ画像、演出、空気感は、まだ人間側の判断がかなり必要です。

Codexだけで完成品の雰囲気を作るというより、Codexで土台を高速に組み、人間がプレイして違和感を潰していくのが現実的だと思います。

# まとめ

今回の範囲では、BABEL-LINK 2060の体験版導線を、資料とスクリプトを使って仮組みしました。

やってよかったのは、いきなりMZ上で作り込まず、次の流れにしたことです。

1. 世界観資料を作る
2. 体験版仕様を作る
3. データベースIDを決める
4. バランス数値を決める
5. スクリプトで一括反映する
6. 監査スクリプトで確認する
7. 実プレイで詰まりを直す

まだ製品版には遠いですが、少なくとも「どこへ向かうゲームか」と「MZ上でどう実装するか」は見えるようになりました。

次は、EV025以降の認可戦本編、戦闘UI、記録保管庫、ビジュアルブラッシュアップを進めていく予定です。
