# AIが「もっともらしい答え」を返す時代に、何を信頼するか

生成AIは、コード、設計、仕様、数学の証明らしき文章まで作れるようになりました。便利になる一方で、AIの出力をそのまま正しいものとして扱うことには、はっきりした限界があります。

AIは候補を高速に出せます。しかし、その候補が本当に要件を満たすか、境界条件を漏らしていないか、推論の途中で飛躍していないかは別の問題です。

そこで重要になるのが、AIに答えを作らせることと、その答えを**機械で検証すること**を分ける考え方です。Lean 4 は、この検証側を担えるプログラミング言語兼対話的定理証明支援系です。

この記事では、Lean を使い始めるためのチュートリアルではなく、AI時代に Lean による検証がなぜ意味を持つのかを、後から読み返しても分かるように整理します。

## 先に結論

Lean が重要なのは、AIの出力を「それらしく見える文章」から「仕様に対して検査可能な成果物」へ変えられるからです。

ただし、Lean は万能の真実判定器ではありません。保証されるのは、**Lean に書いた仕様と前提のもとで、その性質が証明されていること**です。要件そのものが間違っていたり、現実の業務ルールをモデル化し忘れていたりすれば、Lean はそこを自動で補ってはくれません。

この限界を理解したうえで使うと、Lean は AI を過信しないための強力な土台になります。

# AIの得意なことと、検証が必要なこと

AIが得意なのは、過去のパターンから候補を作ることです。

- コードのたたき台を書く
- テストケースを考える
- 仕様を文章にまとめる
- 証明の方針を提案する
- 既存コードの問題点を指摘する

どれも開発を速くします。一方で、次の問いには候補の生成だけでは答え切れません。

- この実装は、例外ケースを含めて要件を満たすか
- この認可処理では、本当に権限のない操作が起きないか
- この金額計算で、負の値や端数の扱いは正しいか
- この推論は、途中の前提を飛ばしていないか

通常のテストは、選んだ入力例についての振る舞いを確かめます。これは不可欠です。ただし、テストしていない入力が必ず存在します。

形式検証では、対象の性質を論理式として表し、その性質が成り立つことを証明します。Lean は、書かれた証明をカーネルが検査する仕組みを持ちます。タクティクスや自動化が証明を組み立てても、最終的には生成された証明項がカーネルに受理されなければ成立しません。[Lean Language Reference](https://lean-lang.org/doc/reference/latest/) は、この最小カーネルが証明項を検査し、タクティクスの不具合がそのまま健全性を壊さない設計を説明しています。

# Lean 4 は何をする道具か

Lean 4 は、依存型理論を基盤にした対話的定理証明支援系であり、同時に実用的な関数型プログラミング言語でもあります。数学の定理だけでなく、ソフトウェア、ハードウェア、プロトコルが仕様を満たすことを記述し、証明できます。[Theorem Proving in Lean 4](https://lean-lang.org/theorem_proving_in_lean4/introduction.html) でも、形式検証を「システムの主張を数学的に表現し、その成立を証明する」営みとして説明しています。

2026年8月時点で、安定版の最新リリースは Lean `4.33.0` です。エディタの応答性、`try?` による証明提案、`lia` と `grind` タクティクスなどが改善されています。[Lean 4.33.0 release notes](https://lean-lang.org/doc/reference/latest/releases/v4.33.0/)

Lean を使うときに押さえるべき役割は、次の3つです。

| 要素 | 役割 |
| --- | --- |
| 定義 | 扱うデータや処理を曖昧さなく書く |
| 命題 | 守りたい性質・業務ルールを表す |
| 証明 | その性質が定義から導けることを示す |

AIは、この3つを一緒に提案できます。ただし採用されるのは、Lean が検査を通せたものだけです。

# 最小の例: 「証明がないと使えない関数」

次の例では、支払額が正であることを確認できた場合だけ承認処理を呼べるようにします。

```lean
structure PaymentRequest where
  amount : Nat

def IsValid (request : PaymentRequest) : Prop :=
  0 < request.amount

def approve (request : PaymentRequest) (_ : IsValid request) : Nat :=
  request.amount
```

`approve` の第2引数は、ただの真偽値ではありません。`request.amount` が 0 より大きいという**証明**です。

```lean
def validRequest : PaymentRequest := { amount := 5000 }

example : IsValid validRequest := by
  decide

example : approve validRequest (by decide) = 5000 := by
  rfl
```

ここで重要なのは、`approve` を呼ぶ側が「有効である」という根拠を渡さなければならないことです。

もちろん現実の決済や業務システムは、これだけでは足りません。通貨、上限、承認者、状態遷移、外部APIの失敗などを定義に追加する必要があります。それでも、守りたいルールを型と命題の形に近づけることで、単なるコメントやレビュー依存だった前提を、コンパイル・検証の対象にできます。

# AIとLeanを組み合わせるときの役割分担

AIとLeanは競合しません。むしろ相性がよい組み合わせです。

```text
人が決める       何を守るべきか、どこまで形式化するか
        ↓
AIが提案する     定義、補題、証明方針、実装候補
        ↓
Leanが検証する   仕様と前提のもとで証明が成立するか
        ↓
人がレビューする 仕様の妥当性、現実の業務とのずれ、採用判断
```

AIに任せやすいのは、反復的で探索量の多い部分です。

- 型やデータ構造のたたき台を作る
- 小さな補題を分解する
- 証明戦略を複数出す
- Lean のエラーを読んで次の修正候補を出す
- テストと証明の対象範囲を比較する

人が持ち続けるべきなのは、何を正しさと呼ぶかの決定です。たとえば「この承認フローでは、誰の承認が必要か」「障害時に何を許容するか」は、コードや証明を書く前の設計判断です。

# 形式検証が特に効く場所

すべてのコードを最初から Lean で証明する必要はありません。まずは、間違えると被害が大きい、または仕様の解釈がぶれやすい部分を選ぶのが現実的です。

- 権限・認可
- 金額、請求、割引、税計算
- 状態遷移
- データ整合性
- 暗号、プロトコル、フォーマット変換
- AIエージェントが実行する操作のガード条件

たとえば AI エージェントに業務操作を任せる場合でも、「提案はできるが、実行には必要な承認と状態がそろっている」という制約を明示できます。AIの自由度を上げるほど、どの操作を許可し、どの条件を必須にするかを機械的に確認できる価値が上がります。

# Leanで保証できること、できないこと

Lean の導入で最も避けたいのは、「証明済みだから現実でも絶対に安全」と考えることです。

## 保証できること

- Lean に記述した定義・公理・仕様のもとで、証明が通っていること
- 証明に必要な前提を型や命題として要求できること
- 変更によって証明が壊れたとき、検査で検出できること

## 保証できないこと

- そもそもの要件が正しいこと
- 仕様に書かなかった例外や業務ルール
- 外部API、データベース、UI、運用手順との接続部分
- 信頼基盤の外にある実装の不具合

だからこそ、Lean はテスト、レビュー、監査、運用設計の代替ではなく、追加の防壁として使います。AI時代には、生成速度だけでなく、どの層で何を検証するかを設計することが重要です。

# まず始めるなら

最初の目標は、大きなプロダクトを丸ごと形式化することではありません。

1. 重要な業務ルールを1つ選ぶ
2. 入力・状態・期待結果を文章で書く
3. そのルールを小さな Lean の定義と命題にする
4. 例と反例を作る
5. 証明が壊れる変更を1つ入れて、Lean が止めることを確認する

Lean の公式学習リソースには、プログラマ向けの [Functional Programming in Lean](https://lean-lang.org/functional_programming_in_lean/) と、証明の基礎を扱う [Theorem Proving in Lean 4](https://docs.lean-lang.org/theorem_proving_in_lean4/) があります。はじめは文法を覚えることより、「自分が守りたいルールを1つ書ける」ことを目標にすると進めやすいです。

# まとめ

AIは、実装と推論の候補を大量に作る能力を持っています。しかし候補が正しいことと、もっともらしく見えることは同じではありません。

Lean 4 による検証は、AIの出力を無条件に信頼するための仕組みではなく、**信頼してよい範囲を明確にするための仕組み**です。

AIに速く作らせ、人が守るべき性質を定め、Lean にその成立を検査させる。この分担ができるほど、AIを実務へ深く入れるときの安全性と説明可能性を高められます。
